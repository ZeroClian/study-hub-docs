# Git 常用命令文档重组设计

## 目标

重组现有 `docs/devops/git.md`，让读者能够先通过总览判断问题类型，再进入对应分册完成操作。文档重点覆盖日常协作、分支整合、回退恢复和冲突处理，并把 SSH、HTTPS、代理、认证和网络问题统一归入远程异常排查。

完成后，读者应能够：

1. 按工作场景找到命令，而不是从无序命令列表中猜测。
2. 区分正常 Git 操作与异常排查流程。
3. 在回退、合并和冲突处理中判断操作是否会改写历史或影响远程分支。
4. 在执行高风险命令前确认工作区、暂存区、当前分支和远程状态。
5. 在操作完成后使用只读命令验证结果。

## 采用方案

采用“保留现有入口页 + 新增五个场景分册”的总分结构。`docs/devops/git.md` 继续作为专题总览并保留现有 `/devops/git.html` 路由，避免已有链接失效；详细内容放入 `docs/devops/git/` 子目录。

不采用以下方案：

- 继续维护单篇长文：文件最少，但合并、回退、冲突和连接异常会再次混杂，难以扫读。
- 仅拆成“正常操作”和“异常处理”两篇：分类清楚，但单篇仍会同时承担多个工作流，后续扩展性不足。
- 每个 Git 命令单独成页：颗粒度过细，读者必须先知道命令名称，无法从实际问题出发查找。

## 文档结构

保留并重写总览页，新增五个分册：

- `docs/devops/git.md`：专题总览、场景导航、安全检查清单、命令选择原则和推荐阅读路径。
- `docs/devops/git/daily-workflow.md`：仓库初始化、克隆、查看状态、暂存、提交、拉取、推送、历史和差异查看。
- `docs/devops/git/branch-integration.md`：分支创建与切换、`merge`、`rebase`、`cherry-pick` 的适用场景、操作流程与取舍。
- `docs/devops/git/rollback-recovery.md`：`restore`、`reset`、`revert`、`reflog` 的影响范围，以及未提交、已提交、已推送三类回退场景。
- `docs/devops/git/conflict-resolution.md`：冲突识别、冲突标记、逐文件解决、继续或放弃 `merge`、`rebase`、`cherry-pick`。
- `docs/devops/git/remote-troubleshooting.md`：远程地址、SSH、HTTPS、代理、认证、连接超时和受限执行环境排查。

总览不重复各分册的完整命令，只保留决策入口、最低限度的安全检查和相对链接。每项知识由一个分册负责，其他页面使用相对链接引用。

## 统一内容模板

每个分册按以下顺序组织：

1. 适用场景：说明这一页解决什么问题，以及不适合什么情况。
2. 正常操作：按“操作前检查 -> 执行 -> 结果验证”给出命令和解释。
3. 异常处理：按“现象 -> 常见原因 -> 诊断 -> 恢复或放弃”组织。
4. 风险提示：说明是否改写提交历史、是否影响远程、是否需要团队协作。
5. 场景速查：用表格建立“需求或现象 -> 推荐命令或处理入口”的映射。

命令示例使用占位符，如 `<branch>`、`<commit>`、`<remote>` 和 `<file>`。危险操作不提供可直接误用的真实分支或绝对路径。

## 操作与异常边界

“正常操作”描述预期工作流，包括创建分支、提交、同步、合并、回退一个明确变更和解决已知冲突。“异常处理”只处理操作未按预期完成的情况，包括：

- 工作区不干净导致切换、合并或变基失败。
- `merge`、`rebase` 或 `cherry-pick` 进入冲突状态。
- 错误提交、错误暂存、错误重置或提交丢失后的恢复。
- 非快进推送、远程分支落后、认证失败和网络超时。
- Git 配置、本机代理与受限执行环境之间的责任边界不清。

正常流程中的 `--abort`、`--continue` 和恢复命令放在对应操作之后，但统一标记为异常恢复动作，避免与成功路径混写。

## 命令选择原则

文档突出以下判断，避免只罗列命令：

- `merge` 保留分支关系，适合共享分支整合；`rebase` 整理本地未共享提交，避免默认对公共历史变基。
- `cherry-pick` 迁移少量独立提交；依赖链较长时优先评估合并分支。
- `restore` 处理文件和暂存区；`reset` 移动本地分支指针；`revert` 用新提交撤销已共享变更。
- 已推送历史优先使用 `revert`；只有团队明确协调后才讨论带租约的强制推送。
- 提交疑似丢失时先使用 `reflog` 定位，不立即清理仓库或继续重写历史。
- 远程访问失败时先用只读命令诊断，不直接修改全局代理、凭据或远程地址。

## 安全与验证

涉及合并、回退、冲突和远程操作的步骤，统一要求先确认：

```bash
git status --short --branch
git branch --show-current
git log --oneline --decorate -n 10
git remote -v
```

具体场景只选用必要检查，不机械要求执行全部命令。操作后通过 `git status`、`git log`、`git diff`、`git show` 或 `git ls-remote` 验证，不以命令退出码为唯一成功证据。

文档必须明确警示以下操作：

- `git reset --hard`
- `git clean -fd`
- `git push --force` 与 `git push --force-with-lease`
- 删除分支或标签
- 修改全局代理、凭据和 URL 重写规则

这些命令仅在解释适用条件、影响范围和更安全替代方案后出现。文档不引导读者把敏感 Token、带认证信息的代理地址或完整凭据输出到日志和聊天中。

## 验收标准

1. 总览页可以按“日常操作、分支整合、回退恢复、冲突处理、远程异常”进入对应分册。
2. 五个分册均包含适用场景、正常操作、异常处理、风险提示和场景速查。
3. 合并、回退和冲突内容同时覆盖开始操作、验证结果、继续和放弃路径。
4. 回退文档明确区分工作区、暂存区、本地提交和已推送提交。
5. 远程异常文档先诊断后修改配置，并区分 Git、环境变量、系统代理和受限执行环境。
6. 所有跨页 Markdown 链接使用相对路径，现有 `/devops/git.html` 入口继续有效。
7. 侧栏和知识地图均能发现专题总览与各分册。
8. `git diff --check`、`pnpm docs:validate`、`pnpm docs:build`、CI 模式构建和渲染结果验证全部通过。
9. 生成的 Git 专题页面无失效链接、代码围栏错误或明显重复内容。

## 非目标

- 不编写 Git 内部对象模型、协议实现或源码分析教程。
- 不覆盖 GitHub、GitLab、Gitee 各自的 Pull Request 或权限管理界面。
- 不把复杂历史整理、仓库迁移、子模块和 Git LFS 展开为完整教程。
- 不修改站点 `base`、域名、主题或其他技术分类。
- 不提交或推送正文改造结果，除非用户后续明确要求 Git 交付。
