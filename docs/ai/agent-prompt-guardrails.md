# AI 智能体提示词校验与可靠性

文章将内容按“问题 → 校验分层 → 可复制模板 → 验收清单”重新组织。适用于 Codex、Claude Code、PiAgent 等能够调用工具、修改文件或连续执行多步任务的通用智能体。

## 核心观点

提示词负责把智能体引向正确方向，校验项负责把错误结果挡在交付之前：

> **提示词决定上限，校验决定下限。**

不要只要求智能体回答“是否完成”，而要要求它提供可以检查的证据：来源链接、实际运行输出、修改前后对比或独立复核结果。

## 为什么需要校验围栏

智能体并不是只回答一次问题，而是会连续进行查找、判断、执行和总结。每一步都有偏离任务的可能，最后的“已完成”并不能证明结果正确。常见风险包括：

- **多步执行跑偏**：中途的错误决策会被后续步骤放大。
- **事实幻觉**：文章、报告中的数据、日期、人名和引用可能看似合理但无法验证。
- **假成功**：工具或模型返回成功，实际文件、命令或数据却没有达到预期。
- **自我确认偏差**：在同一上下文中复查自己的答案，往往只会重复原来的判断。
- **模型变化导致规则失效**：依赖某种措辞的提示词可能随着底层模型升级而失灵。

校验围栏不能保证结果绝对正确，但能把“我觉得完成了”变成“我能证明完成了”。

## 五层校验围栏

按任务风险选择校验强度。层级越高，耗时和 token 成本通常越高，但发现问题的能力也越强。

| 层级 | 围栏名称 | 核心要求 | 适用场景 |
| --- | --- | --- | --- |
| L1 | 输出围栏 | 交付前按清单检查格式、字段和完整性 | 普通草稿、低风险整理 |
| L2 | 事实围栏 | 为关键事实提供来源，区分已验证与待核实 | 文章、报告、资料汇总 |
| L3 | 执行围栏 | 实际打开文件、运行命令或执行测试，并展示结果 | 文件修改、代码和表格处理 |
| L4 | 独立核查围栏 | 使用新的会话或上下文重新检查，不沿用原判断 | 发布、提交和重要交付 |
| L5 | 评审围栏 | 让另一个智能体或独立角色专门挑错 | 高影响、高代价任务 |

低风险任务通常使用 L1 + L2；涉及文件、代码或数据时至少加入 L3；要提交给客户、领导或外部系统的成果，建议使用 L1 至 L5。

## 可直接复用的提示词模板

以下模板可以直接追加到原始任务之后。使用时，把“文中”“目标文件”“原任务”等占位描述替换成具体内容。

### 1. 写文章或报告：事实围栏

```text
【事实校验要求】
1. 文中每个事实性陈述（数据、日期、人名、公司名、引用）都必须标注真实、可打开的来源链接。
2. 完成初稿后，列出全部事实性断言，逐条回答“我是否确定这条为真？依据是什么？”。
3. 无法确认的内容要删除，或改写为“据公开资料显示”并标注“待核实”。
4. 文中区分【已验证】和【待核实】；文末单独列出待核实清单。
5. 禁止用“大约”“据统计”等模糊表达掩盖缺少来源的问题。
```

### 2. 修改文件或表格：执行围栏

```text
【执行校验要求】
1. 动手前先用三句话说明：修改哪些文件、每个文件改什么、如何验证。
2. 每完成一步都实际打开或运行验证，并贴出关键原始输出，不要只说“看起来没问题”。
3. 完成后展示修改前后 diff，并说明每处改动的原因。
4. 任一步失败、报错或结果不符合预期时，停止后续操作，报告失败详情，禁止声称已完成。
5. 最后单独回答：所有步骤是否都经过实际验证？未验证项是什么？
```

### 3. 查资料或做调研：交叉验证围栏

```text
【调研校验要求】
1. 每个关键结论至少使用两个相互独立的来源支持；只有一个来源时标注“单一来源”。
2. 来源优先级为：官方文档或官网 → 权威机构报告 → 行业媒体 → 个人博客。
3. 不同来源存在矛盾时，原样列出矛盾，不要自行调和。
4. 无法直接打开验证的内容，放入“未验证清单”，不得混入已确认结论。
5. 先输出结论，再输出证据清单，并标明每条结论对应的来源。
```

### 4. 重要交付：独立复核围栏

最好在新的会话中执行下面的复核提示词，避免复核者受到原执行过程的影响：

```text
你是独立质量审查员。下面是一份由另一个 AI 完成的成果，请用挑剔的眼光审查。

【成果】
粘贴成果内容或文件摘要

【原任务】
粘贴原始任务要求

请检查：
1. 事实错误：逐条核对数据、日期、人名和引用，指出可疑项；
2. 逻辑漏洞：检查论证是否自洽，有没有偷换概念或明显跳跃；
3. 完成度：对照原任务逐项确认是否完成；
4. 最后给出结论：通过 / 有条件通过（列出必须修改项）/ 不通过（列出理由）。
```

### 5. 开工前：先写验收标准

```text
【验收标准】
开始执行前，先输出一份验收清单，不要立刻动手。清单必须包含：
1. 交付物是什么（文件、报告、数据或修改后的内容）；
2. 每项交付物的合格标准，必须是可以检查的具体条件；
3. 你打算如何逐项验证这些标准（打开文件、运行检查或对比 diff）。

执行完成后，对照清单逐项标记通过或未通过；未通过项必须说明原因，不得笼统声称任务完成。
```

## 推荐工作流

对于需要可靠交付的任务，可以固定采用下面的顺序：

1. **定义任务**：说明目标、范围、禁止事项和交付物。
2. **写验收标准**：把“准确”“完整”“质量高”改成可检查的条件。
3. **分级加围栏**：根据风险加入事实、执行、独立核查或评审要求。
4. **执行并留证**：保留来源、命令输出、测试结果和 diff。
5. **独立复核**：高影响任务使用新上下文或另一个智能体挑错。
6. **对照交付**：逐项确认验收标准，未通过项如实标注。

## 实践清单

- 要证据，不要承诺：把“确认没问题”换成实际输出或可复现的验证结果。
- 明确允许失败：写明“不确定就直说，禁止编造”，让智能体可以安全地停下来。
- 校验必须具体：“确保内容准确”不可检查；“每个数据都有可打开的来源链接”才是有效标准。
- 真的独立复核：使用新会话、不同角色，必要时换用更强的模型。
- 按风险投入：低风险任务轻量校验，高影响任务完整启用五层围栏。
- 亲自查看关键交付物：围栏降低风险，但不能替代对重要文件和结果的最终确认。
